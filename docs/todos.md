# 대화의 할 일 목록

여러 단계 요청에서 봇이 `todo_write`로 만든 작업 목록을 현재 답변 바로 위에 표시합니다. 목록은 읽기 전용이며, 제목을 클릭하거나 키보드 Enter/Space로 접고 펼칠 수 있습니다. **대기**, **진행 중**, **완료**, **취소됨**을 텍스트와 아이콘으로 구분합니다. 진행 중 항목을 강조하고 완료 개수를 표시합니다. 다크·라이트·시스템 테마와 좁은 화면을 지원합니다.

## 상태 계약

`GET /api/state`와 상태 스트림의 `conversations[].run.todos`는 선택 필드입니다.

```json
{
  "todos": [
    { "content": "자료 확인", "status": "completed" },
    { "content": "결과 검토", "status": "in_progress" }
  ]
}
```

- `status`: `pending`, `in_progress`, `completed`, `cancelled`.
- 필드 없음: 아직 이 턴의 계획을 받지 않았거나 이전 형식의 상태입니다. 새 턴은 이 상태로 시작합니다.
- `[]`: 엔진이 명시적으로 빈 목록을 보냈습니다. 화면에는 빈 카드 대신 아무것도 표시하지 않습니다.
- 매 계획은 전체 목록을 교체합니다. 같은 목록을 반복해 받아도 항목을 덧붙이지 않습니다. 화면에는 현재 턴의 마지막 목록 하나만 표시하며 이전 답변별 목록을 따로 보여 주지 않습니다.
- 완료·취소·오류·중단 시 마지막 목록을 보존합니다. 새로고침과 서버 재시작 뒤에도 저장된 목록을 보여 줍니다. 접기 상태는 현재 화면에서만 유지됩니다.
- 항목은 모델이 보고한 진행 상태입니다. 답변 종료 자체를 각 항목의 완료로 취급하지 않습니다. 미완료 항목은 상태를 그대로 두고 실행 종료 후 회전 표시만 멈춥니다.
- 본문은 Markdown/HTML이 아닌 일반 텍스트입니다. 기존 공개 텍스트 제한(항목당 최대 200,000 UTF-16 코드 단위)과 자격 증명 마스킹을 적용합니다.

## 엔진 경계

고정한 Grok Build `2bdd1d6a6369`의 안전한 기본 도구 `todo_write`만 기존 `search_tool`/`use_tool` 프로필에 추가합니다. 셸·네이티브 파일 도구·하위 에이전트와 기존 승인 경계는 바꾸지 않습니다. 세션 프로필 변경 때문에 기존 실행 세션은 다음 턴에 최근 표시 기록을 포함한 새 세션으로 전환됩니다. 저장된 대화 화면 기록은 유지합니다.

엔진 도구 입력은 `todos: [{id, content?, status?}]`와 선택 `merge`이며, `merge`의 기본값은 `true`입니다. 부분 업데이트의 병합은 엔진이 담당합니다. 네이티브 도구의 성공 출력은 ID를 포함한 전체 상태와 순서 있는 전체 항목 배열을 담습니다. 앱은 **현재 턴의 성공한 호출에서 언급한 ID**만 그 성공 상태에서 골라 저장합니다. 재시작 후 엔진이 예전 도구 상태를 읽어도 이전 턴의 ID를 자동으로 표시하지 않습니다. 원시 입력만으로 내용·상태를 만들거나 실패한 호출의 ID를 추가하지 않습니다. 중복 내용과 숫자 ID도 전체 출력 배열의 순서와 현재 항목 개수를 유지합니다.

네이티브 성공 출력을 사용하지 않는 실행에서는 영속 **ACP Plan**을 대체 경로로 지원합니다. 네이티브 도구가 현재 턴의 목록을 공급한 뒤에는 뒤따르는 전체 세션 Plan으로 덮어쓰지 않습니다. ACP에서 취소된 항목은 엔진의 `_meta.cancelled`를 읽어 `cancelled`로 복원합니다.

고정 엔진의 영속 Plan 알림에는 바깥 `_meta.eventId`가 있습니다. 턴 종료 시 미완료 항목을 완료처럼 보이게 만드는 임시 알림에는 이 식별자가 없으므로 앱은 저장·표시하지 않습니다. 이 구분은 고정한 엔진 버전의 계약이며, 엔진을 올릴 때 통합 테스트와 함께 다시 확인해야 합니다.

## 재현 가능한 검증

- `npm run build`, `npm test`.
- `npm run test:rust`: 모델의 이전 상태 호환·네 상태 직렬화, 완료/중단/빈 목록 재시작, 공개 상태 마스킹, 실제 엔진과 모의 공급자를 통한 HTTP 목록 업데이트.
- `npm run test:e2e:rust -- tests/todos.spec.ts`: 1040/390/320 px에서 표시·진행 변경·병합·반복·교체·취소 상태·키보드 접기·테마·긴 항목·새로고침·서버 재시작·새 턴 초기화·미완료 보존.
- 실제 엔진 테스트는 부분 업데이트·거절된 중복 ID·빈 목록·동일 세션 새 턴의 새 ID·임시 완료 알림도 검증합니다.

## 실제 모델 확인과 지침 결정

2026-11-02에 임시 데이터·작업 폴더와 실제 `gpt-6.1-sol`을 사용했습니다. 기존 설정은 변경하지 않고 자격 증명은 서버에서만 사용했습니다. 요청에 도구 이름을 넣지 않았으며, 실제 공급자 요청에서 모델·도구 목록·추가 지침의 적용 여부만 검증했습니다.

| 동일한 자연어 요청 | 추가 지침 없음 | 추가 지침 있음 |
| --- | --- | --- |
| 3단계 릴리스 절차를 글로 정리하고 검토하기 | 2회 모두 목록 없이 답변 | 짧은 목록 안내를 넣은 2회 모두 목록 없이 답변 |
| 작업 폴더 구성 확인 → 두 파일 읽고 요약 → 차이·보완점 검토 | 1회, 실제 `todo_write` 4회와 네 단계별 상태 스냅샷 | 더 명시적인 지침을 넣은 1회도 실제 호출 4회와 네 상태 스냅샷 |

파일 점검에서 추가 지침 없이 `진행 중/대기/대기 → 완료/진행 중/대기 → 완료/완료/진행 중 → 모두 완료`를 관찰했습니다. 마지막 완료는 임시 정리 알림이 아닌 **모델의 실제 상태 갱신 호출**로 확인했습니다. 파일 내용은 바뀌지 않았고 디스크의 최종 목록도 상태 응답과 같았습니다.

따라서 이번 변경에서는 **모든 대화에 별도 목록 지침을 추가하지 않습니다**. 기존 엔진 도구 설명만으로 실제 다단계 작업의 사용을 확인했고, 간단한 문서 작성 답변까지 목록을 강제할 근거는 부족합니다. 이 여섯 관찰은 한정된 정성 검증이며 모든 요청에서의 사용률을 보장하지 않습니다. 재현용 요청 예:

> 작업 폴더를 3단계로 점검해 줘. 먼저 파일 구성을 확인하고, 다음으로 notes.txt와 nested/readme.md의 내용을 읽어 핵심을 정리한 뒤, 마지막으로 두 파일 내용의 차이와 보완할 점을 검토해 줘. 각 단계 진행 상태도 보여 줘. 파일은 수정하지 마.

같은 모의 공급자 시나리오의 실제 앱 Before/After 화면은 이 변경의 PR에 정리합니다. 모의 공급자는 전달·저장·표시 계약을 확인하고, 위 실제 모델 관찰은 모델의 자발적 도구 사용을 별도로 확인합니다.

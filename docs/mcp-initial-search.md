# MCP 초기 도구 검색과 초기화 대기

## 확인한 문제

PR #37의 OAuth 검증 중 첫 `search_tool({"query":"notion search","limit":5})`가 빈 `partial`을 반환했습니다. OAuth 중계기·검증용 공급자 수정과 별개로, 일반 모델을 사용하는 Rust 런타임의 시작 순서도 조사했습니다. 계정 토큰이나 실제 Notion 검색 내용은 이 조사에 사용하거나 기록하지 않았습니다.

고정한 Grok Build `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`에서 ACP `session/new`와 `session/load`의 응답은 MCP 도구 검색 인덱스의 완료를 보장하지 않습니다. 기본 progressive 초기화가 별도로 진행되고, `search_tool`은 호출 시점의 인덱스를 즉시 읽습니다. 다른 시작 모드의 짧은 유예나 이벤트 큐 비우기도 전체 도구 목록의 준비를 보장하지 않습니다.

`total_hidden_tools`는 모든 MCP 서버의 현재 인덱스 합계입니다. 보고된 `8a23399`의 앱 자체 `workspace` 브로커에도 20개 도구가 있으므로, `20`이라는 값만으로 Notion 도구 등록을 확인할 수 없습니다. 현재 기본 브랜치에는 캔버스 도구 두 개가 추가되어 앱 도구가 22개입니다.

“모든 문서에 notion이 있어 BM25 점수가 0”이라는 가설은 해당 버전의 구현과 맞지 않습니다. 잠긴 `bm25 2.3.2`의 IDF는 `ln(1 + (N - df + 0.5) / (df + 0.5))`이며 모든 문서에 있는 용어도 양수입니다. 도구명 하이픈·밑줄 분할과 정확한 이름 일치 경로도 이미 있습니다. 초기화되지 않은 Notion 도구는 정확한 이름으로 검색해도 아직 찾을 수 없습니다.

## 변경한 시작 순서

Rust 런타임은 새 세션과 저장 세션 모두에서 ID를 먼저 기록한 뒤, 기존 ACP 확장 `x.ai/mcp/list`를 `sessionId`와 `cache:true`로 조회합니다. `result.sessionMcpResolved`가 명시적인 `true`가 된 다음에만 모델에 프롬프트를 보냅니다. 이 값은 마지막 검색 인덱스 발행 뒤에 설정됩니다.

- 서버 하나의 `ready`, 도구 개수, 이전 초기화 알림으로 완료를 추측하지 않습니다.
- 대기는 기존 시작 제한 시간(기본 30초)과 중단 경로 안에서 수행합니다. 추론 무응답 제한 시간을 소비하지 않습니다.
- 250ms 간격의 상태 조회이며 인증 재시도나 `tools/call` 재전송이 아닙니다. 각 조회만 엔진에 맡기므로 대기가 취소된 뒤 별도의 조회 루프가 남지 않습니다.
- 초기화 완료는 모든 서버의 성공이 아니라 시도의 종료를 뜻합니다. 실패한 서버 없이 대화를 계속하는 기존 동작과 도구별 한 번 승인은 유지합니다.
- 상태 확인 실패·잘못된 응답은 시작 오류로 처리합니다. 내부 구성이나 오류 내용을 사용자 응답에 복사하지 않습니다.

HTTP API·저장 형식·도구 스키마는 바꾸지 않습니다. OAuth 인증·중계기·검증용 공급자는 이 변경에 포함하지 않습니다. 오래 걸리는 연결은 이전보다 첫 모델 요청이 늦어지며, 전체 시작 제한 시간을 넘기면 불완전한 인덱스로 진행하는 대신 시작 오류로 끝납니다. Node 백엔드의 시작 순서는 이 Rust 런타임 변경의 대상이 아닙니다.

## 재현과 검증

기본 회귀 검사는 실제 Rust 앱·네이티브 엔진과 인증 없는 합성 Notion HTTP MCP를 사용합니다. 즉시 도구를 요청하는 공급자를 두고 `tools/list`를 3.5초 지연합니다.

```sh
node scripts/cargo.mjs test --locked -p grok-bot-core --test mcp_initial_search
```

변경 전 첫 검색은 `results: []`, `total_hidden_tools: 22`, `status: "partial"`로 재현했습니다. 이는 앱 도구만 있는 인덱스입니다. 새 세션·저장 세션에서 준비된 합성 도구의 검색, 호출 전 한 번 승인, 연결 실패 후 대화 지속, 초기화 중 중단, 시작 제한 시간도 같은 검사에서 다룹니다.

실제 모델도 선택해 실행할 수 있습니다. 아래 변수는 명시적으로 지정할 때만 사용하며, 기본 검사와 CI는 외부 모델을 호출하지 않습니다. 외부 모델 호출에는 공급자 비용이 발생할 수 있습니다. 모든 대화·도구 응답은 합성 데이터이며 실제 계정에는 접근하지 않습니다.

```sh
MCP_SEARCH_LIVE_MODEL='<model-id>' \
MCP_SEARCH_LIVE_BASE_URL='<OpenAI-compatible-base-url>' \
MCP_SEARCH_LIVE_API_KEY="$YOUR_PROVIDER_KEY" \
MCP_SEARCH_DELAY_MS=9000 \
node scripts/cargo.mjs test --locked -p grok-bot-core --test mcp_initial_search -- --nocapture
```

`grok-4.7-build-fast` 실제 추론으로도 변경 전 9초 지연에서 첫 검색의 빈 `partial`을 확인했습니다. 같은 모델의 3.5초 지연에서는 모델 응답 전에 도구가 준비되어 `ready`가 나왔습니다. 따라서 실제 모델에서도 발생 가능한 타이밍 문제이지, 모든 호출에서 반드시 나타나는 현상은 아닙니다.

변경 후 같은 실제 모델·9초 지연으로 새 세션과 저장 세션을 다시 실행했습니다. 두 첫 검색 모두 합성 Notion 도구를 포함한 `total_hidden_tools: 24`, `status: "ready"`였고, 각각 한 번 승인한 뒤 호출이 완료되었습니다. 연결 실패 후 대화 지속과 초기화 중 중단·시작 제한 시간 검사도 통과했습니다. 이 합성 검증은 실제 Notion OAuth 계정 검증을 대신하지 않습니다.

# 여러 단계 Bot 전달과 후속 답변

Rust 백엔드의 Bot 전달 계약입니다. Node 백엔드는 후속 보고를 제공하지 않으며, 이 저장 형식으로 기록한 상태는 이전 버전/Node 백엔드에서 열 수 없습니다. Rust 서버는 공개 상태에 `runtime.botMessageChains: true`를 알리며, UI는 이 표시가 없는 서버에 대기 체인용 작업 중단을 노출하지 않습니다.

## 하위 결과를 기다리는 전달

A가 B에게 보내고 B가 C에게 다시 물으면 다음 순서로 실행합니다. 모든 턴은 [Bot별 FIFO와 전역 동시 실행 상한](per-bot-concurrency.md)을 사용하며, 하위 결과를 기다리는 부모는 실행 자리를 점유하지 않습니다.

1. A의 승인된 전달이 B의 읽기 전용 수신 대화에서 실행됩니다.
2. B가 C에게 보내고 현재 턴을 마치면 A→B 전달은 `waiting_children`이 됩니다. B의 임시 답변을 최종 답변으로 교환 기록에 복사하거나 A에게 보고하지 않습니다. 대기 중에는 실행 슬롯을 점유하지 않습니다.
3. C가 끝나면 B의 같은 수신 대화에서 숨김 보고 입력과 후속 답변 한 쌍을 추가합니다. C의 답변·상태·오류는 다른 Bot의 대화 데이터로 인용하며, 시스템 지시로 취급하지 않습니다.
4. B의 정리 턴과 그 턴에서 시작한 하위 전달까지 모두 끝나면 B의 마지막 답변만 A→B 교환에 한 번 기록합니다. 그다음 A의 원래 대화에서 후속 정리가 한 번 실행됩니다.

수신 대화는 계속 사용자 메시지를 받을 수 없는 대화 전용 공간입니다. 파일·컴퓨터·비공개 스킬·외부 MCP 권한이 추가되지 않습니다. **새로운 Bot 전달**은 매번 승인을 묻고, 후속 턴에서도 자동 허용 규칙은 중지됩니다. 앱이 결과를 넣는 숨김 보고 입력 자체는 새 전달이 아니므로 별도 승인하지 않습니다. 그룹·스레드·루틴 대화에는 최상위 보고를 추가하지 않습니다.

## 보고 한도와 hop 한도

- 일반 사용자 턴에서 시작한 첫 전달은 자신의 ID를 `chainId`로 쓰고 hop 1에서 시작합니다. 수신 턴이나 후속 보고 턴이 다시 보내는 전달은 같은 체인을 유지하고 원인이 된 전달의 hop에 1을 더합니다. 수신 대화의 후속 턴에서는 방금 보고받은 하위 전달이 원인입니다. 따라서 B의 수신 대화로 돌아왔다고 hop이 초기화되지 않습니다.
- 전달 깊이는 기존처럼 최대 **4 hop**입니다. 5번째 hop의 메시지는 승인/저장 전에 거절합니다. 체인 전체 전달도 **최대 14건**으로 명시해 승인 전과 저장 전에 검사합니다. 전달당 수신 턴/보고 턴은 각각 한 번이므로 최초 사용자 턴을 포함한 체인 처리 턴은 **최대 29개**입니다(모델의 도구 호출/보조 요청 수와는 다릅니다). 기존 4-hop/최상위 보고 2건에서 가능한 8+4+2의 분기 상한을 넘기지 않습니다.
- 원래 일반 대화에 보고를 예약하는 횟수는 체인당 **최대 2건**입니다. 대기/실행 중인 보고와 완료·실패·취소·중단된 보고 모두 예산을 사용하며 재시도하지 않습니다. 이미 2건을 사용한 뒤 전달이 끝나면 전달 결과는 보존하되 그 보고는 `skipped`로 끝내고 새 턴을 시작하지 않습니다. 추가 질문을 반복하는 루프를 막는 한도입니다.
- C→B처럼 상위 전달을 완성하는 데 필요한 **수신 대화 내부 정리 턴은 이 2회에 포함하지 않습니다**. 4-hop 체인의 결과가 보고 예산 때문에 중간에서 잘리지 않습니다.
- 각 전달의 보고는 한 번만 시작합니다. 대화에서 가장 오래 기다린 체인의 현재 대기 보고를 한 턴에 묶으며, 다른 체인의 보고는 다음 턴으로 남깁니다. 묶인 보고에서 다시 보낼 때는 가장 높은 hop을 원인으로 삼고, 동률이면 보고 입력에 먼저 나온 전달을 선택합니다(기존 저장 상태와 같은 규칙).

B는 결과가 준비된 하위 보고부터 이어서 답할 수 있습니다. 예를 들어 B가 C의 hop 2 결과를 보고받는 중 D에게 다시 보내면 새 전달은 hop 3입니다. B의 그 턴은 끝나더라도 A→B는 계속 기다리고, D의 결과를 반영한 B의 마지막 정리가 끝나야 A에 보고합니다. 모든 자식 결과가 모일 때까지 중간 정리 턴 자체를 막는 방식은 아닙니다.

## Stop과 체인 전체 기한

처음 전달이 승인되어 저장된 시점부터 체인 전체에 **30분**의 wall-clock 기한이 적용됩니다. 대기열, 모델 실행, 승인 대기, 하위 전달, 후속 정리 시간이 모두 포함됩니다. 하위 hop이나 서버 재시작은 기한을 새로 시작하지 않습니다. 스케줄러가 기한을 확인하고, 새 전달/턴의 시작에서도 만료 여부를 확인합니다.

**작업 중단**은 선택한 대화의 현재 모델 실행과 이미 대기 중인 작업만 취소합니다. 다른 Bot이나 같은 Bot의 다른 대화, 독립적으로 접수된 하위 전달을 함께 취소하지 않습니다. 기다리는 부모가 현재 실행이나 대기 보고를 갖고 있지 않다면 Stop은 하위 Bot의 실행에 영향을 주지 않습니다. 이는 이슈 #20의 명시적 대화 범위 규칙으로 변경한 동작입니다.

체인을 기다린다는 이유만으로 Bot의 실행 자리를 잡지 않습니다. 다른 Bot은 빈 전역 자리에서 동시에 실행하며 같은 Bot의 별도 사용자 메시지는 동일 FIFO에 접수합니다. 대기 항목 하나의 취소와 대화 전체 Stop은 구분합니다. 화면의 다중 실행·대기 상태 전환은 별도 UI 단계에서 적용합니다.

체인 루트의 선택적 `chainTermination`은 여전히 **체인 전체 기한 만료**를 디스크에 먼저 기록하는 데 사용합니다. 시간 초과는 오류로 기록하고 해당 체인의 새 자동 보고를 억제합니다. 이미 승인해 실행한 외부 변경을 되돌리는 기능은 아니며, 같은 대화의 무관한 사용자 턴도 중단하지 않습니다.

| 종료 원인 | 상위로의 처리 |
| --- | --- |
| 하위 Bot 실행 실패·중단·재시작 복구 | 하위 전달의 상태/오류를 부모의 후속 턴에 한 번 전달합니다. 부모가 이를 설명해 정상 종료하면 그 설명을 상위에 보고합니다. |
| 부모의 정리 턴 실패·중단 또는 시작 실패 | 부모 전달도 해당 실패/중단 상태로 끝납니다. 임시 답변은 복사하지 않고 그 상태를 상위에 한 번 보고합니다. 실행 오류는 종속 하위 작업을 정리하지만, 대화 Stop·재시작은 다른 대화에 이미 접수된 작업을 취소하지 않습니다. |
| 선택한 대기 보고 취소 | 요청에 표시한 전달 ID 중 아직 대기 중인 보고만 취소합니다. 최상위 대화에서는 다른 도착 보고와 원래 대화/전달을 유지합니다. 수신 대화의 선택 보고를 취소해 하위 결과를 정리하지 못하면 부모 전달은 `cancelled`로 끝나고 그 비성공 상태를 상위에 한 번 보고합니다. 중간 답변은 성공으로 올리지 않으며 취소된 수신 작업이 소유한 나머지 대기도 정리합니다. 이 의존 관계는 취소 버튼의 안내에 표시합니다. 이미 다른 대화에 접수된 하위 전달은 유지합니다. |
| 대화 Stop | 선택한 대화의 현재 실행과 대기 항목만 취소합니다. 다른 대화의 전달/보고는 독립적으로 유지합니다. |
| 30분 만료 | 해당 체인의 미완료 전달을 오류로 끝내고 대기 보고는 `skipped`로 마칩니다. 실행 중 보고도 종료하며 새 상위 모델 턴은 만들지 않습니다. |

## 저장·복구

수신 대화는 최초 발신 Bot 입력/답변 한 쌍과, 저장된 하위 보고에 연결된 숨김 입력/답변 쌍을 허용합니다. 보고 대상 Bot 삭제로 참조가 지워진 과거 입력은 빈 보고 표식을 유지해 계속 숨깁니다. 임의의 사용자 입력을 허용하도록 메시지 수 검사만 제거하지 않습니다. `executionRunId`는 마지막 수신 처리 턴에 연결되지만 `startedAt`은 최초 수신 실행 시각을 유지합니다. 후속 턴은 보고 ID/실행 ID와 대화 기록의 연결을 별도로 검증합니다. 이전 PR 버전이 마지막 턴으로 덮어쓴 시각도 읽을 수 있고, 진행 중인 전달은 최초 입력의 저장 시각으로 정규화합니다.

대기 전달과 대기 보고는 재시작 후 이어갑니다. 시작했던 모델 턴/보고는 `interrupted`로 끝나며 재실행하지 않습니다. 중간 정리 턴이 시작하지 못하거나 실패하면 이전의 임시 답변을 성공 결과로 올리지 않습니다. 내부 정리가 완료된 뒤 다시 하위 작업을 기다리다가 Stop/기한 종료/다음 정리 시작 실패가 발생하면, 대화의 현재 상태는 전체 작업의 종료를 표시하되 이미 완료한 보고 기록은 그대로 보존합니다. 이 불일치는 같은 체인의 종료 래치 또는 정확히 연결된 시작 실패 기록으로 증명되는 경우만 저장 검증에서 허용합니다.

PR #9에서 이미 완료된 전달은 새 기능으로 다시 열거나 누락된 하위 보고를 소급 실행하지 않습니다. 기존 `skipped` 기록도 유지합니다. 이전 보고 기능의 `state.json.pre-bot-reports.bak`은 그대로 보존합니다. 이 기능의 `waiting_children`/`chainTermination`, 수신 대화의 보고 또는 추가 보고 기록을 처음 저장하기 전에는, **이미 PR #9 보고를 쓰는 상태도** 별도의 `state.json.pre-bot-chains.bak`(0600)으로 한 번 보관합니다. 기존 백업은 교체하거나 심볼릭 링크를 따라가지 않으며, 새 백업을 안전하게 만들 수 없으면 이전 상태 파일을 새 형식으로 덮어쓰지 않습니다.

전달을 예약할 때 답변/오류 복사본의 실제 상한을 확보하고, 후속 보고 시작 전에는 숨김 입력의 실제 JSON 크기와 실행 후 답변/오류 여유를 다시 검사합니다. 64MiB 안에 안전하게 들어가지 않는 보고는 상태를 변경하기 전에 거절하고 보고 시작 실패로 처리합니다. 이미 보관된 대화/전달을 지우거나 저장소를 영구 오류 상태로 만드는 방식은 사용하지 않습니다.

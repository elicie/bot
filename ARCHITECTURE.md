# Local Grok Bot architecture

## Understood as

Build a browser application with the Grok Bot desktop layout, configurable OpenAI-compatible inference through Grok Build, and intentional editing of local files on the backend computer. Implement the renderer independently and verify real browser behavior and disk changes.

## Data ownership

[shared/types.ts](<shared/types.ts>) defines the frontend's public bots, conversations, messages, routines, routine executions, tool activities, pending permissions, runtime state, settings, and text documents; [crates/model](<crates/model/>) holds the Rust state models. The Rust backend is the single writer of durable application state. Grok Build owns ACP execution sessions. The application stores session IDs and a display transcript. API keys stay in the backend data directory and provider relay, not in browser snapshots or the engine configuration.

## Runtime

One Rust executable, `grok-bot`, runs an axum HTTP server for both the React frontend and the API. There is no Node backend. The default bind address is `127.0.0.1`; explicit `HOST=0.0.0.0` enables trusted-network access. The backend validates Host, port, and Origin against its explicit allowlist. The application has no login. SSE carries public state snapshots with a persisted monotonic revision. Changes publish after their atomic state write succeeds. The frontend rejects snapshots older than its current revision. HTTP commands mutate settings, bots, conversations, approvals, and workspace documents. The active run states are `starting`, `running`, and `awaiting_permission`. Terminal states are `completed`, `cancelled`, `error`, and `interrupted`.

[engine/src/host.rs](<engine/src/host.rs>) is a library host directly linked to `xai-grok-shell` from pinned Grok Build source. Its `!Send` agent lives on a dedicated OS thread with a current-thread Tokio runtime and `LocalSet`. ACP (Agent Client Protocol) stays as the internal contract over in-memory duplex pipes; channels connect the engine thread to the server. The engine starts lazily and is reused between turns. There is no standalone engine binary, per-turn engine subprocess, Node↔Rust ACP boundary, or upstream CLI composition root. The app owns host configuration and lifecycle; Grok Build supplies the agent loop, model sampler, tool dispatch, and saved execution sessions.

When configuration and engine source match, the runtime loads the conversation's saved ACP session. A changed fingerprint starts a new session and passes up to 64 KiB of recent visible user/assistant history as quoted conversation context. Existing messages and original execution files stay intact. One app-private HOME/GROK_HOME/XDG environment is prepared before threads start and isolates configuration and state from the user's other Grok installations. The selected custom model uses `chat_completions`. The curated agent profile keeps file operations behind the app-owned HTTP MCP (Model Context Protocol) broker and disables ambient native file/shell tools; instruction skills and the native todo tool do not add file permissions. Writes retain the category rules and one-use approvals described below. Cancellation settles pending permissions and sends ACP `session/cancel`; an in-process engine is not a process that the server can kill independently. Automatic retries are disabled so provider failures reach the UI promptly. The backend enforces a 30-second inactivity deadline, pauses it while a user approval is pending, and resets it on actual ACP updates. The application still admits one active run globally; the P0 multi-session experiment does not change that policy. Source provenance, licensing, and build gates are recorded in [docs/source-engine.md](<docs/source-engine.md>).

## Build and deployment

The root [Cargo workspace](<Cargo.toml>) and [Cargo.lock](<Cargo.lock>) cover the server, core, engine library, models, store, and files. [scripts/cargo.mjs](<scripts/cargo.mjs>) prepares the native build environment and invokes locked workspace commands. Node.js 22.12+ is build/test tooling for the frontend and scripts, not a production backend runtime. `npm run build` builds only the frontend. `npm run dev` builds the frontend and starts the Rust debug server; it does not imply HMR. `npm start` runs the Rust debug server through the Cargo wrapper without rebuilding the frontend.

`npm run build:release` runs the frontend build followed by `node scripts/cargo.mjs build --locked --release -p grok-bot-server`. [crates/server/build.rs](<crates/server/build.rs>) embeds the compiled [dist/](<dist/>) for release builds; a release build requires `dist/index.html` to exist first. The resulting `target/release/grok-bot` serves its embedded assets from any working directory with no Node/npm, external frontend directory, or separate engine executable. An explicit `GROK_BOT_WEB_ROOT` overrides the default frontend source and must contain `index.html`. Debug builds do not embed frontend files: they serve [dist/](<dist/>) from the current working directory, or run API-only when it is absent. Their build script does not watch frontend output, so creating or removing it does not trigger Rust rebuilds.

Embedded content-hashed Vite assets use a one-year immutable cache policy; HTML and unhashed assets revalidate. ETags support bodyless 304 responses to conditional GET/HEAD requests. The embedded SPA fallback excludes the decoded `/api` and `/internal` namespaces at exact path boundaries, not unrelated routes such as `/internals`.

The release profile is `opt-level = 3`, `debug = 0`, `strip = "debuginfo"`, and `panic = "unwind"`: debug information is removed but function symbols remain available for backtrace names. Aborting panics would bypass engine-thread unwinding; this is not a claim of complete recovery from every engine failure. Single-executable deployment is not a static-link or cross-platform guarantee: compatible Linux native libraries, including libc and zlib, remain required. Managed browsing additionally needs system Google Chrome and a working sandbox. `grok-bot --help`, `--version`, and `--licenses` expose usage, build identity, and embedded original source notices. Normal startup takes no arguments and uses environment configuration; unsupported flags and positional arguments are rejected. Redistribution must retain applicable notices and satisfy the final dependency graph's license and source-availability obligations; the embedded upstream notices are not a complete release compliance inventory. Current commands, earlier P4 evidence, and rebased-review checks are separated in [docs/verification.md](<docs/verification.md>).

## Conversation canvas

An optional `Conversation.canvas` stores one current text/code document plus the most recent 20 prior immutable versions. Each save uses a document-local expected revision; creation expects zero, and restore appends a new increasing revision. Dedicated canvas HTTP commands may save while a model run is active without relaxing workspace-file idle guards. They preflight the complete candidate state before mutation. The Node and Rust canvas paths share the wire shape, 128 KiB text bound, exact unique nonempty `oldText` range anchor, Unicode/CRLF preservation, and conflict semantics.

Authenticated `read_canvas` and `replace_canvas_range` infer the exact conversation from the run. A replacement captures complete old/new range text and always waits for one-use approval outside the command queue, then rechecks cancellation, revision, range uniqueness and protected text under the final store mutation. A stale approval cannot overwrite a newer user save. Recipient bot-delivery conversations remain chat-only. Public current/history text is redacted and affected versions are read-only; browser drafts also detect same-revision projection changes caused by secret configuration. Tool reads page the public UTF-8 content through the existing literal-data escaping boundary; the complete serialized wrapper is at most 18 KiB to stay below the engine's 20,000-byte inline limit. Continuations require the document revision and a hash of its public view so secret changes cannot mix pages. Full export assembles every page before the existing file approval. Workspace export uses the unchanged `read_file`/`write_file` hash and approval path; download is browser-only. Canvas restore does not revert exported files. See [docs/canvas.md](docs/canvas.md) for HTTP/tool inputs, UI behavior, retention and the old-binary rollback limitation.

## Private skills

Each bot optionally owns persisted instruction skills with a generated ID, name, description, complete Markdown instructions, enabled state, and optimistic revision. User mutations pass through the existing command queue and idle guard. Model `create_skill` proposals require a complete one-use review; denial or cancellation writes nothing. Authenticated broker `list_skills` and `read_skill` infer ownership from the run, enforce enabled state, and deny private-skill access in recipient bot-delivery conversations. Skill content grants no new tools or permissions. Enabled-content fingerprints replace execution context after changes while retaining visible chat history.

The app uses instruction-only records and a strict SKILL.md text importer. Native filesystem discovery, native Skill/read aliases, plugin extension forwarding, shell tools, and executable Rhai workflows remain disabled. The source audit and remaining connector/publishing gaps are recorded in [docs/skills-gap-audit.md](<docs/skills-gap-audit.md>).

## Routines

A routine selects one bot, a prompt, and a one-time, interval, or daily IANA-timezone schedule. The app-owned scheduler shares the serialized HTTP command queue. It persists each conversation, immutable execution metadata, and schedule advance atomically before starting the existing runtime. Only one execution is active globally. Each routine admits one queued or active execution, and missed recurring times coalesce.

`RoutineRun.executionRunId` binds history to the original execution; terminal `RoutineRun.result` survives follow-up messages in the same conversation. Startup recovery interrupts started work without replay and resumes durable queued claims. Pausing keeps accepted work, and deletion keeps execution history and conversations. See [docs/routines.md](<docs/routines.md>) for the scheduling and recovery contract.

Each routine can hold one webhook key. Only a SHA-256 hash is stored (the public snapshot omits even that). `POST /hooks/routines/:id` lives outside `/api` because external senders cannot send `Origin` or `X-Grok-Bot`; it authenticates `Authorization: Bearer <key>` with a constant-time hash comparison, throttles repeated failures per routine, and claims a `webhook`-trigger run through the same admission as a manual run. An optional body (at most 16 KiB of UTF-8) is appended to the prompt inside a `<webhook_payload>` block marked as untrusted data. Host and Origin validation still apply, so LAN senders need `HOST=0.0.0.0` and an allowed host. Webhook runs leave the schedule untouched, and pausing a routine stops only scheduled runs.

## Permission rules

Rules map an action category (`file_write`, `bot_message`, `bot_create`, `skill_save`, `memory_save`, `mcp_tool`; `mcp_tool` rules may name one custom MCP `server`) for all bots or one bot to "항상 묻기" (`ask`, the default) or "묻지 않고 허용" (`allow`). Ask rules win conflicts. Every broker mutation calls `Runtime::approve_category`, which records an allowed action's tool activity with `approvedByRule` (shown as "내 규칙으로 자동 승인됨") instead of showing a card. Rules never lift the safety floor: local-only approvals always ask, bot-delivery recipient conversations and webhook-triggered runs always ask, and hash, size, hop, and recipient checks run before approval. The server has no login, so only a loopback client may add or loosen allow rules; LAN clients may view rules and tighten them.

## Vault secrets and custom MCP servers

The vault ("보관함") holds named secrets (`^[A-Z][A-Z0-9_]{0,63}$`, values 8–8192 characters without control characters) for every bot or for one bot. Values are write-only from the browser: they are stored in `state.json` (mode 0600, like the provider API key; there is no OS keychain integration and no encryption at rest), the public snapshot carries only `{ id, name, botId?, createdAt, updatedAt }`, and every snapshot string, streamed assistant text (split-prefix holding for every key), tool activity, error, and model-facing history is redacted of the API key and every secret value (`State::redaction_keys`, longest first). The minimum length keeps redaction from mangling ordinary text.

Each bot may hold up to 10 custom MCP servers, edited as one "MCP 서버 JSON" document in the common `{"mcpServers": {"name": {"command", "args", "env"} | {"url", "headers"}}}` shape (the bare server object is accepted too). Validation is strict: names `^[a-z0-9][a-z0-9_-]{0,31}$` without `__` and not starting with `workspace` (the engine joins server and tool names with `__` and pre-allows only `MCPTool(workspace__*)`), duplicate keys rejected, unknown fields rejected, absolute or `PATH` commands, `http`/`https` URLs without credentials, bounded sizes. Env and header values may reference secrets as `${secret:NAME}` (the bot's own secret wins over an all-bots secret); they are resolved only when a turn starts and reach only the in-process engine's ACP `mcpServers`. The snapshot shows `{ name, transport, enabled, secretRefs }` only; the JSON itself (which may hold literal values) is served to loopback clients only.

The server has no login and a stdio server is arbitrary command execution as the server user, so every secret change and every MCP change that can make a server run (saving the JSON, enabling) requires a loopback client. New and changed servers start disabled; disabling is allowed from LAN. Enabled servers join the bot's sessions next to the `workspace` broker (recipient bot-message conversations get none) with a 10 s startup and 25 s call timeout, and their enabled configuration (unresolved, so no secret values) is part of the session fingerprint. A server with a missing secret or a missing command is skipped and an engine `x.ai/mcp/server_status` report of an unavailable server becomes a failed tool activity; the turn continues. Each custom tool call arrives as an ACP permission request that becomes an approval card ("MCP 서버 name: tool"); declining it sends the engine a follow-up so the model continues without the tool. A `mcp_tool` permission rule (all servers or one `server`, all bots or one bot) can allow calls without asking, except in webhook-triggered runs. Stdio servers inherit the server process environment (with `HOME` pointing at the engine home) plus their configured `env`. Tool results from a custom server reach the model unfiltered; a server that echoes its own credentials exposes them to the model (they stay redacted in the browser).

## MCP apps

Successful custom MCP tools may attach a bounded `ToolActivity.mcpApp` from their definition's `_meta.ui.resourceUri`. The runtime reads that exact `ui://` HTML resource through the existing session-scoped engine extension before closing the turn. The store keeps the resource with its actor bot and server record/version, validates UTF-8/count limits, and redacts HTML plus JSON-encoded input keys/values. Historical HTML remains viewable after its server is disabled or removed.

Only these persisted app cards opt into JSON-RPC `postMessage`; ordinary visualization fences gain no tool authority. The renderer reuses the script-only opaque iframe, network-blocking CSP and full-screen viewer. Each app call creates a separate expiring one-use request and host approval; model `mcp_tool` rules never auto-approve it. After explicit approval the backend serializes a bounded target-only MCP session with model execution, rechecks the saved binding/current configuration, dispatches through the existing engine proxy without an LLM prompt or workspace broker, and closes it. Model `Conversation.run` remains unchanged. The pinned engine exposes text content, not full structured results or a complete app-only catalog; unsupported targets fail closed. See [supported behavior and limits](<docs/mcp-apps.md>).

## Bot messages

`BotExchange` stores a two-bot transcript and `BotDelivery` stores its durable, idempotent execution receipt. The authenticated broker exposes bot discovery and an outbound message proposal. Approval records the full recipient/text before creating the recipient's dedicated conversation and queue entry atomically. A single source run can deliver one distinct message. Each further hop needs fresh approval. Chains stop at four hops and fourteen total deliveries, bounding recipient/report turns plus the origin at twenty-nine.

The recipient runs under its own identity with file and computer tools denied. When it delegates again, its delivery waits in `waiting_children` without occupying the execution slot. Each child result starts a hidden report turn in that same recipient conversation; only the final answer after those continuations is projected once into the exchange. Dedicated recipient conversations reject user-prompt hijacking. The routine dispatcher admits both routine claims and bot deliveries in FIFO order under the same global execution slot. Queued deliveries survive startup; started deliveries become interrupted without resend. Pair transcripts use query routing and preserve the originating chat draft.

Follow-up ("report") turns tell the sender what came back. When a delivery sent from a plain 1:1 conversation finishes (completed, error, cancelled, or interrupted), store reconciliation sets its `report` to `queued`. Deliveries sent from a live recipient conversation are reported there before its owning delivery can complete, so A→B→C unwinds C→B→A. Group, thread, and routine sources are not reported. The dispatcher treats every source conversation with queued reports as one FIFO work item, ordered by the time the delivery finished. It starts the item when no run is active, and a user turn that started first runs first. `Runtime::start_report` runs one turn of the sender bot in its original conversation. Queued reports of the oldest chain in that conversation become `running` in the same turn; unrelated chains never share a new report turn. The hidden user input (`Message.reportDeliveryIds`) quotes each recipient's name, status, error, and answer as JSON labelled conversation data from another bot. The chat hides that input and shows a "…의 답변을 받아 이어서 답함" marker above the reply. The report run's outcome is projected onto the report (`completed`, `cancelled` by Stop, `error`, or `interrupted` by a restart). A report is never retried. A turn that cannot start ends its reports as `error`. Permission rules never auto-approve actions in a report turn, the same safety floor as recipient and webhook runs. A message sent from a report turn's answer continues the reported delivery's chain (`chain_parent`: same `chainId`, hop + 1), so the four-hop limit still applies. A chain gets at most two reports in its original conversation; mandatory recipient continuations are exempt, so the four-hop limit does not truncate the return path. Later discretionary reports are marked `skipped`. A root-only `chainTermination` records Stop or the fixed 30-minute wall-clock deadline durably before cancelling the active engine; queued descendants/reports are settled without replay. The scheduler checks deadlines even while a run or approval is active, and admission checks the same original chain start time. `executionRunId` tracks the current recipient handling turn while `startedAt` preserves its first start; recipient transcripts allow only their initial pair plus child-report-linked input/answer pairs. Legacy completed deliveries are never reopened for retroactive reports. See [the chain contract](docs/bot-message-chains.md). Deleting a bot drops its deliveries' pending reports and the deliveries chained from its report turns. Surviving report messages keep an empty marker. The legacy pre-reports backup remains unchanged. Before first writing `waiting_children` or `chainTermination`, the immediately preceding disk state (including an existing PR9 reports disk) is separately secured as `state.json.pre-bot-chains.bak` (0600, no-follow, never replaced); failure blocks the incompatible write. Pending deliveries reserve bounded answer/error copies and report start measures the actual hidden JSON input plus future answer/error growth before mutation.

`POST /api/conversations/:id/bot-reports/cancel` requires strict `{deliveryIds: string[]}` (1–10,000 UUIDs) under the usual same-origin mutation guards and returns `{state: AppState, cancelledDeliveryIds: string[]}`. There is no `{}` cancel-all fallback. It shares the scheduler's command queue and atomically cancels only requested reports still `queued` in that source conversation (`status: cancelled`, `finishedAt`, no `runId` or hidden input); for ordinary root sources, unrequested later arrivals remain executable. IDs that no longer match a queued report are ignored, and an empty result makes the UI explain that nothing was cancelled. Missing conversations return 404. Running reports and messages remain unchanged. For ordinary root sources, delivery receipts and conversation runs are unchanged too. If a selected queued report belongs to a waiting recipient, its aggregate delivery ends cancelled rather than publishing a provisional success; that non-success is reported upstream once and any remaining work owned by the cancelled recipient is retired. The nested action's tooltip discloses this dependent-parent cancellation. Whole-chain Stop remains separate. Persistence validation permits an unstarted cancellation only without a hidden report message. Both dispatch and report planning select only `queued` reports, so cancellation survives restarts without replay. Each message-summary action sends only its displayed delivery ID and says “이 보고 취소”. Report live regions are limited to queued chips; running/terminal chips opt out of the enclosing log's announcements. Already-started reports are not falsely marked cancelled.

Before the first write of a cancelled report without a run ID, the ordered writer preserves the preceding compatible state as `state.json.pre-unstarted-report-cancellation.bak` (0600, create-once/no overwrite, synced before replacing state). Failure to create this required backup aborts the write through the normal persistence-failure path. This is separate from the pre-reports backup and protects report-aware older binaries, which reject unstarted cancellations. An installation already containing this newer shape cannot retroactively obtain a compatible backup; startup does not label a copy of it as rollback-safe. Restoring a backup is a manual whole-state rollback and loses later changes.

## Group chats and threads

A `Group` lists 2–12 member bots in speaking order, plus a name, color, and avatar shape. It appears in the sidebar beside the bots. A group conversation stores the group ID in both `botId` and `groupId`, so routines, deliveries, and 1:1 runs cannot resolve it as a bot.

Each user message opens a round. If the message mentions members by whole name (`@Name`, case-insensitive, not inside a word), only those members answer. Otherwise every member answers. In both cases members answer in member order, once each. Their replies never start further member turns, so bots cannot loop.

The first member takes the user's turn. The remaining members are stored durably in `Conversation.groupRound.pendingBotIds`. The dispatcher starts each one as FIFO work under the single global execution slot. The runtime wakes the dispatcher whenever a run settles.

Every answer records its speaker in `Message.speakerBotId` and runs under that member's identity, instructions, and skills. Each member has its own engine session (`Conversation.memberSessions`, `grok/<conversation>/<bot>/<fingerprint>`). A member whose session is loaded receives the transcript since its last reply. A member starting a fresh session receives the bounded transcript so far. Either way the transcript arrives as quoted JSON conversation data.

Stopping or failing a member turn also clears the members still queued. Cancelling between turns does the same. Member edits and group deletion wait for an idle app and a finished round. Deleting a group removes its conversations and threads and keeps its bots. Loading `state.json` drops members whose bot no longer exists, and `State::remove_bot_from_groups` does the same at runtime. Hidden bots stay members.

A thread is a conversation linked to one message (`Conversation.thread`). It inherits the parent's `botId` and `groupId`, so a thread of a group conversation is answered by the group. A message has at most one thread, and threads cannot be nested. A fresh thread session receives the parent message and up to eight preceding messages as quoted data, bounded to 12 KiB each. Threads open beside the main chat (full screen below 760 px) through the `thread` query parameter. Group routes use `?group=&conversation=&thread=`.

## Managed computer

`shared/computer.ts` defines a typed 960 × 600 browser surface. `ManagedComputer` owns a fresh private Chrome, an ephemeral profile, a mandatory verified sandbox, an authenticated loopback proxy, and a public-origin allowlist. Request UUIDs are one-use; epoch and frame UUIDs prevent stale actions. Public-address validation covers all DNS answers, and the proxy pins the selected validated address. HTTP methods, credentials, sensitive controls, downloads/uploads, workers, WebSockets, WebRTC, and native OS actions are restricted. Browser sandbox verification fails closed.

`ApplicationComputer` associates the single browser with a bot, caches local PNG frames, and adds cancellation generations so Stop invalidates pending work across both command queues. HTTP starts/actions share model-run admission. Stop bypasses that queue to interrupt slow navigation. Computer HTTP routes and model permission decisions require a loopback socket; forwarded-address headers grant no trust. LAN snapshots and SSE replace local-only approval/tool details with a content-free stub. Cached PNGs bind to the exact epoch/frame, and coordinate clicks stay disabled until that image loads. Cancellation stops only the browser epoch used by the run. A reverse proxy requires separate authentication and remains outside the deployment contract. Model computer tools operate only on a user-started browser and request one-use local approval for every observation/action. The provider receives redacted URL/title/control text and coordinates; the browser preview uses PNGs locally.

## Read state, deletion, attachments, and rich text

Read state is server-side: `Bot.unread` in `state.json`, shared by every browser and kept across reloads and restarts. A run that finishes as `completed` or `error` marks its bot unread in the same commit; cancellation does not. The browser showing that bot (chat view, visible tab) marks it read again when the answer arrives or when the bot is opened. A manual "읽지 않음으로 표시" stays until the bot is opened again. `Bot.notifyOnUpdates` is per bot on the server; each browser shows a `Notification` only when it holds permission in a secure context (HTTPS or localhost; LAN HTTP falls back silently with a notice). The message sound is a per-browser preference (`localStorage`), synthesized with Web Audio. Read-state and notification changes are allowed during runs.

Deleting a bot requires an idle application (no active run), no queued routine run of the bot or its routines, no queued or running bot message in its delivery graph, and at least one other bot. One commit removes the bot with its skills, its conversations, its routines and their routine history, every delivery and exchange it sent or received plus the deliveries chained from those, the read-only recipient conversations those deliveries created for other bots, and links from surviving messages to removed exchanges. The candidate state must pass the same reference validation as `state.json` loading before it is committed. Afterwards the server removes the deleted conversations' attachment blobs and private engine session directories (`<data>/attachments/<id>`, `<data>/grok/<id>`). Engine-internal session records under the shared `GROK_HOME` are not pruned.

Attachments are sent with `POST /api/conversations/:id/attachment-messages` (base64 JSON, body limit raised for this route only). Limits: 8 files, text 256 KB each and 512 KB together, images (PNG, JPEG, GIF, WebP by signature) 5 MB each, 10 MB per message. `state.json` keeps only metadata on the user message; bytes are owner-only blobs under `<data>/attachments/<conversation>/<attachment>`, served back as `text/plain` or the image type under a sandboxing CSP. Text files reach the engine inside the text prompt as a `<user_attachments>` section of JSON lines whose string values escape `@`, `[`, `:`, and `<`, and the combined text still passes `literal_engine_prompt`, so attachment contents cannot trigger upstream `@path` expansion, `data:` image extraction, or slash commands. Images become ACP image blocks; the pinned Grok Build accepts them although it does not advertise `promptCapabilities.image`, normalizes them, and sends them as Chat Completions `image_url` data URLs (pinned by `crates/core/tests/integration/attachments.rs`). Replacement sessions replay only attachment names.

Assistant Markdown renders KaTeX math (`$…$`, `$$…$$`, `trust: false`) and Mermaid fences (`securityLevel: 'strict'`, shown as an `<img>` of the generated SVG). Both libraries load on first use; formulas that fail show their source, and diagrams that fail show their code. Raw HTML stays skipped.

The Rust server runs the engine against a loopback provider relay (own random port, per-process bearer token) instead of the provider itself. The relay forwards requests with the real API key, which never reaches the engine configuration, streams responses through, and turns OpenRouter-style `images` (generated images with no `content`, which the engine would treat as an empty reply) into images stored under `<data>/generated-images` and linked from the reply text. Unreferenced generated images are swept after a one-hour grace period.

## File access

Chat needs a configured provider and model. File access additionally needs an explicitly selected workspace. HTTP and MCP reads and writes use the same confined file service and reject symbolic links, hard links, traversal, binary documents, and oversized files. Linux opens parent directories through pinned descriptors and uses no-follow flags. Explicit Save uses a content hash to detect external changes. The agent runs in an app-private working directory and accesses the user workspace through the MCP broker. Native file tools, shell execution, subagents, and external tools are disabled. The profile declares its exact discovery/invocation tools and disables ambient instruction-file discovery. Attachment-shaped text and leading slash commands are delegated as a literal JSON string so upstream's pre-tool parser cannot expand local paths or dispatch native commands. The visible transcript preserves the original text. This is application-level confinement. It does not claim an OS sandbox against other programs running as the same user.

## Implementation ownership

- [crates/server](<crates/server/>) owns the executable, CLI, and embedded frontend packaging.
- [crates/core](<crates/core/>) owns HTTP/SSE, runtime admission, MCP broker, scheduling, managed browsing, and provider relay; [engine](<engine/>) owns the in-process upstream host. Backend tests live with the Rust workspace.
- [crates/model](<crates/model/>), [crates/store](<crates/store/>), and [crates/files](<crates/files/>) own persisted models, atomic state, and confined file access.
- [web](<web/>) owns the React frontend. [tests](<tests/>) retains frontend unit tests and Playwright acceptance tests; Node backend unit tests were removed. Rust backend coverage is not a claim of one-for-one replacement: scheduler concurrency gaps identified in review require explicit regressions and current-head verification, tracked in [the verification record](<docs/verification.md#rebased-review-verification>).
- Shared contracts, root configuration, documentation, and end-to-end tests stay aligned across those boundaries.

## Verification predicates

A browser user configures a local mock OpenAI-compatible endpoint, connects a disposable workspace, sends a prompt through the source-linked application engine, observes tool status, approves or denies a write, and checks exact disk contents. Reopening the page preserves bots and conversation history. Cancellation ends the task. Traversal and symlink paths fail. Provider failures appear in the UI. Desktop and mobile controls stay usable. Approved bot delivery executes a recipient and persists its pair transcript. Managed Chrome supports actual browsing and typed control while private-address and stale-frame actions fail; Stop interrupts navigation. The user authorized original-window capture and the observed states were compared. Complete-product pixel parity remains unverified across independent assets, local extensions, and unobserved states.
